# Selection 交互规则

## 目的

本文档用于明确 `code-view-compose` 中选区、滚动、长按菜单与平台分层的规则，避免后续在 Android / Desktop 上继续把不同输入模型混在一起实现。

这里讨论的范围包括：

- caret 放置
- 范围选区
- 滚动与选区手势优先级
- 长按后的菜单入口
- Selection Handle 手柄拖拽
- 平台桥接边界

不包含：

- 复杂编辑命令系统
- 双击选词 / 三击选行的完整桌面语义补全
- Android 原生 `SelectionToolbar` 具体 UI 形态实现

## 核心结论

### 1. 不直接按“平台名”写业务分支

- 不在公共编辑逻辑里到处写 `if (isAndroid)` / `if (isDesktop)`。
- 平台差异通过 `PlatformEditorBridge` 这类桥接层收口。
- 公共层只依赖“交互能力”或“输入模型”，而不是平台名本身。

当前已经落地的能力开关：

- `useFloatingInputAnchor`
- `useTouchSelectionGestures`

这两个开关表达的是：

- 输入宿主是否需要作为浮动锚点
- 选区手势是否应该按“触摸优先”处理

### 2. Selection 模型分成两类

#### Mouse-first

适用于：

- Desktop / 鼠标主导场景

规则：

- 主点击放置 caret
- 按下后拖拽直接扩展选区
- 次键触发上下文菜单
- 滚动主要依赖滚轮 / 触控板滚动，而不是按住内容拖动

#### Touch-first

适用于：

- Android / 触摸主导场景

规则：

- 单击只放置 caret
- 普通拖动优先交给横向 / 纵向滚动
- 长按进入选区模式
- 长按后先按词选中；若继续按住拖动，可直接扩展首个词级选区
- 松手后再显示菜单入口与 `Selection Handle`
- 选区稳定后可继续通过 `Selection Handle` 精细调整

## 当前已确定的 Android 规则

### 1. 点击

- 单击代码区域时，只放置 caret
- 不直接触发范围选区
- 单击才会主动请求输入焦点并唤起软键盘
- 同时清理旧的 composing 锚点状态
- 单击放置 caret 后，应显示单个光标手柄
- 若当前已有非折叠选区，点击选区内时：
  - 软键盘未显示：保留选区，并重新请求软键盘
  - 软键盘已显示：折叠到点击位置对应的 caret
- 点击选区内且当前走“保留选区”路径时，若平台 `SelectionToolbar` 当前未显示，应重新触发显示
- 只有点击选区外时，当前选区才折叠为 caret

### 2. 滑动

- 普通滑动优先用于横向 / 纵向滚动
- 不能再出现“滑动屏幕就开始选区”的行为
- 这是移动端与桌面端最重要的语义分界

### 3. 长按

- 长按后按词选中
- 长按后若继续按住拖动，主画布应直接跟随扩展选区
- 只有手指抬起后才触发当前菜单入口
- Android 当前优先走平台 `SelectionToolbar`
- `sharedUI` 中的 `CodeContextMenu` 保留为不支持平台工具栏时的过渡实现
- 长按进入选区态时不主动唤起软键盘；如果软键盘原本收起，应继续保持收起
- 长按选区手势进行中，不提前显示双手柄或平台工具栏

换句话说，当前长按触发的是：

1. 进入选区态
2. 生成首个词级选区
3. 按住拖动时持续扩选
4. 松手后再打开菜单入口并显示手柄

而不是：

1. 长按一完成就立刻弹出工具栏和手柄

### 4. 手柄

- 选区手势结束后显示基础双手柄
- caret 折叠态显示单个光标手柄
- 手柄拖拽负责扩展或收缩范围选区
- 光标手柄拖拽负责移动 caret
- 手柄拖拽只改变 `selection`
- 手柄交互开始时需要：
  - 清空当前 composing 锚点
  - 清空 `preferredColumn`
  - 不主动唤起软键盘
- 手柄拖拽期间应临时收起平台工具栏，结束后再按当前选区恢复
- 手柄拖到与对侧交汇后，不能直接丢失选区；应允许继续越过并完成反向选区

### 5. 菜单

当前阶段：

- Android 在支持的平台上优先通过 `PlatformSelectionToolbarBridge` 打开平台工具栏
- 平台工具栏当前先承接：
  - 复制
  - 全选
- 长按回调菜单保留为不支持平台工具栏时的兜底路径
- `sharedUI` 已接通 `selectedText`
- `sharedUI` 已接通“全选”

### 6. Android 输入法选区收尾

- Android 输入法结束选区模式时，可能不会只发送“折叠到当前选区端点”的标准请求
- 实际设备上已经确认存在两类异常收尾：
  - 折叠回旧 anchor
  - 折叠到与当前选区完全无关的 offset
- 这些异常 collapsed `setSelection(...)` 不应直接信任
- 当前实现要求：
  - 若当前仍有非折叠选区，且 IME 发来的 collapsed 位置明显不可信，则按“结束选区并保留当前活动端”处理
  - 对 Android 软键盘 `Shift + 方向键` 选区结束后的尾请求，也按同样规则归一化
- 这里的“当前活动端”以内部 `TextRange.end` 为准
- 因此 Android 侧后续任何新的选区交互实现，都不能假设 `selection.start` 永远是视觉 caret
- Android 软键盘“开始选择”模式下，方向键扩选穿过 anchor 进入逆选时，不能因为选区临时收缩到 anchor 就自动退出选择模式
- 换句话说，“collapsed 到 anchor”与“结束开始选择”不是同一件事；只有显式停止选择，或收到可信的结束选择信号时，才允许退出该模式

后续增强：

- Android 应该逐步从通用 `ContextMenu` 迁移到更接近系统习惯的 `SelectionToolbar`
- 这一步不应该反向污染桌面端菜单模型

## 为什么不能共用桌面拖拽语义

如果把桌面拖拽选区语义直接套到移动端，会出现下面的问题：

- 纵向阅读时，一滑就变成选区
- 横向长行滚动时，滚动和选区无法区分
- 用户很难稳定触发“浏览”与“选择”两种意图
- 后续即使补上手柄，主手势依然会和滚动冲突

因此移动端必须改成：

- 主画布拖动 = 滚动
- 长按 = 进入选区
- 手柄拖动 = 调整选区

## 平台桥接边界

### 当前建议

- 选区状态、手柄几何、按词选中规则，继续放在 `commonMain`
- 是否启用“触摸优先选区”由 `PlatformEditorBridge` 提供能力开关
- 平台工具栏已经通过 `PlatformSelectionToolbarBridge` 单独收口
- 当前阶段不需要为了整套 Selection 状态机再拆新的平台实现

### 何时值得新拆桥接

如果后续要做下面这些能力，应单独补新的平台桥接，而不是继续堆到 `sharedUI`：

- Android 原生 `SelectionToolbar`
- 平台触觉反馈
- 平台级文本工具栏
- 平台级复制 / 分享 / 搜索扩展动作

推荐方向是未来补一个独立桥接，例如：

- `PlatformSelectionToolbarBridge`

而不是在页面层直接判断：

- “如果 Android 就画 A”
- “如果 Desktop 就画 B”

## 与输入锚点的关系

选区交互和 IME 不是同一套状态，但两者必须保持一致：

- 进入长按选区前，应中断旧 composing 锚点
- 手柄拖拽开始时，应清空旧 composing 锚点
- 选区更新后，caret 与 selection 需要同步回上层
- 菜单和手柄都应基于画布当前 viewport 坐标工作

这意味着：

- Selection 不是输入锚点的一部分
- 但 Selection 会影响输入锚点的位置和是否需要重置

## sharedUI 当前约束

当前 `sharedUI` 层已经接通：

- 选中文本提取
- “全选”
- `onSelectionChange` / `onCursorChange` 回写到工作区状态

当前仍然是过渡方案的部分：

- Android 已优先接入平台 `SelectionToolbar`
- `sharedUI` 中的 `CodeContextMenu` 仍作为不支持平台工具栏时的兜底路径
- 工具栏动作当前仍只覆盖复制 / 全选，后续还可以继续扩展

所以现在的正确理解是：

- 底层 `Selection` 手势模型已经按移动端重构
- Android 工具栏主路径已经切到平台实现
- 上层菜单与更多动作仍处于过渡阶段

## 当前阶段验收标准

以下条件满足后，可认为移动端 `Selection` 第一阶段达标：

- Android 单击只放置 caret
- Android 普通滑动优先用于滚动
- Android 长按可以稳定选中一个词
- Android 长按按住拖动时可以直接扩展选区
- Android 长按抬手后可以出现菜单入口
- 长按选区手势结束后可以看到双手柄
- 手柄拖拽能更新选区
- 选中的文本可以复制
- “全选”可以工作
- Desktop 仍保留原有拖拽选区语义

## 后续建议顺序

1. 先做 Desktop 工作区真实页面回归，验证拖拽选区、中文输入、composing 打断、长行横向滚动和 annotation 次键上下文是否稳定
2. 再回 Android 真机 / 模拟器回归，验证长按、手柄、滚动和平台工具栏是否打架
3. 再补自动滚动、手柄越界、长行横向拖拽等细节
4. 最后再评估是否需要扩展平台工具栏动作或保留更多共享层兜底菜单能力，以及双击选词、三击选行等桌面增强语义
