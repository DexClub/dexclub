# code-view 总进度

本页是 `code-view` 文档体系中的单一状态入口。

用途只有两个：

- 说明每个能力域当前做到哪一步
- 为每次会话开始、推进和结束提供统一的状态维护基线

这里不记录完整实现细节，也不保留长时间线流水账。具体设计请进入 `design/`，具体行为契约请进入 `spec/`。

## 状态定义

- `待开始`：还没有进入实际推进
- `已计划`：目标和方向已明确，但尚未开始实现
- `进行中`：已经开始推进，但还没有达到当前验收标准
- `已完成`：达到当前阶段验收标准，后续仅做维护或增量修正
- `阻塞`：存在明确阻塞，短期内无法推进
- `已废弃`：路线已放弃，不再继续

## 会话工作流

本节是 `code-view` 相关工作的统一维护规则。后续每次开始、推进和结束时都应遵守。

### 会话开始

- 每次新的 `code-view` 会话，第一步先检查本页，确认当前进行中的主题、当前目标和下一步
- 若本次要推进的主题在本页中已标记为 `进行中`，或用户描述与“上次没做完 / 可能中断”有关，应检查当前工作区状态
- 工作区检查至少包括：
  - `git status --short`
  - 本次主题对应的相关文件
- 若文档状态与工作区实际状态不一致，应先以代码和工作区事实为准，再修正文档

### 会话推进

- 一旦某个主题从“讨论 / 规划”进入实际推进，应及时更新本页的主题状态、当前目标或下一步
- 任何主题发生状态扭转时，都必须立即更新本页，不能等到后续统一补记
- 状态扭转至少包括：
  - `已计划 -> 进行中`
  - `进行中 -> 已完成`
  - `进行中 -> 阻塞`
  - `阻塞 -> 进行中`
  - `已完成 -> 进行中`
- 更新状态扭转时，不能只改“状态”一列，还应同步检查并更新：
  - 当前目标
  - 最近更新日期
  - 下一步
- 若主题转为 `阻塞`，必须同步写明：
  - 阻塞原因
  - 当前停在哪一步
  - 解除阻塞所需的前置条件
- 若新增了长期设计决议，应同步更新对应 `design/` 文档，而不是只留在对话里
- 若问题已经上升为行为契约、状态模型或验证基线变化，不能只更新本页，必须同步更新对应 `spec/` 或 `design/`

### 会话结束

- 每次会话结束前，都应回看本页并按实际结果更新：
  - 主题状态
  - 当前目标
  - 下一步
- 若本次涉及实现、修复或回归，应补充本次验证情况；至少说明：
  - 已验证 / 未验证
  - 实际执行了哪些测试、构建或手测
  - 若未验证，原因是什么
- 若本次没有做完，应明确保留“现在做到哪一步”和“下一步接什么”
- 若本次已经达到当前阶段验收标准，应及时把状态从 `进行中` 调整为 `已完成`
- `进行中 -> 已完成` 只能在以下条件同时满足时发生：
  - 当前阶段目标已经落地
  - 对应代码、设计或规范更新已经完成
  - 必要验证已经完成，或未验证原因已明确记录

### 意外中断恢复

- 若上次会话可能意外中断，下一次进入时不能直接继续写代码
- 必须先检查本页和工作区，确认：
  - 是否存在未提交修改
  - 是否存在进行中但未落文档的主题
  - 是否存在文档已写但代码未跟上的半成品
- 只有在状态与工作区重新对齐后，才能继续推进

## 维护规则

- 总体状态变化优先更新本页
- 每次新的 `code-view` 会话，第一步先检查本页；必要时同步检查当前工作区
- 每次会话结束前都应更新本页，避免留下未记录的中间状态
- 任何主题发生状态扭转时，都必须立即更新本页，不能只在对话里说明
- `已完成` 必须以当前阶段目标、文档更新和必要验证同时满足为前提，不能只凭主观判断切状态
- `阻塞` 必须写清阻塞原因、当前停点和解除条件，不能只标一个状态
- 每次涉及实现、修复或回归的会话结束前，都应补充本次验证情况
- 单个主题的实现边界与设计更新到对应 `design/` 文档
- 公开行为要求逐步沉淀到 `spec/` 文档
- 若某个主题进入真实实现，先更新本页状态，再开始代码工作
- 若真实工作区回归发现需要调整或重构，先更新本页的状态、当前目标或下一步，再进入较大改动
- 若问题已经上升为行为规范、状态模型或验证基线变化，不能只更新本页，必须同步更新对应 `spec/` 或 `design/` 文档
